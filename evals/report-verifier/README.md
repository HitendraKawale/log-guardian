# Offline report-verifier development packet

This packet prepares a verifier experiment. It does not implement or run a verifier.
Contract: `docs/plans/report-verifier-contract.md`.

## Contents and separation

- `inputs.jsonl`: 14 opaque-ID inputs containing owner question/scope, delivered
  evidence and a proposed report, bound by canonical JSON hashes. These alone may
  be supplied to a future verifier, one item at a time with the host policy.
- `labels.jsonl`: seven expected acceptable reports, six semantic negatives and one
  local-invalid control. Labels identify required defect targets and rationale.
- `manifest.json`: source hashes, source-to-input mappings and transformations.
- `response.schema.json`: proposed structured response shape. Exact coverage and
  semantic checks require a future host adapter; the JSON schema does not perform them.
- `build_packet.py`: offline reproducible builder. This script contains evaluator
  judgments and must not be supplied to a verifier.

Keep labels, this README, manifest source mappings and builder out of model inputs.
Do not ship this directory in runtime images or add it to runbook retrieval.
The production Dockerfiles do not copy evals/. No new public export is added.

Eight entries use original fresh-case reports: four provisionally acceptable and
four with clear reviewed failures. Six use three prior reports paired with explicitly
author-written corrected forms. Eleven reports are archived model outputs; three
are authored corrections, not outputs generated by an improved model.

The acceptable examples include real malicious text that the report did not adopt,
plus source-attributed descriptions that must not be rejected merely for quoting
an instruction. Known negatives cover untrusted authority, unsupported causes,
state-changing advice, citation-support gaps and reversal of source meaning.
A fabricated-ID example must fail the existing local validator without spending on
a semantic verifier. It is excluded from semantic error-detection rates.

## Limits

These are development labels made after seeing outputs and reviews. They are not
held-out evidence or independent human judgments. All paired/corrected forms share
evidence; do not treat fourteen entries as fourteen independent incidents. No
verifier error rate, accuracy, latency or cost has been measured.

Contested backlog-onset and in-band-truncation arguments are not required defects.
The fresh-08 negative uses recommendation safety, not those disputed grades.
Conservative wording in an otherwise supported report is not automatically labeled
unsafe. The acceptable labels can still be challenged by later evidence-based review.

The proposed verifier must be assessed on both missed defects and false rejections.
A second model can follow the same injection, hallucinate a criticism or incorrectly
reject a true claim. Quote membership and well-formed responses do not solve those
semantic problems. No automatic repair or fallback acceptance is proposed.

## Reproduce and check

From the repository root:

```bash
.venv/bin/python evals/report-verifier/build_packet.py --output /tmp/new-verifier-packet
cd evals && ../.venv/bin/python -m pytest tests/test_report_verifier_packet.py
```

Choose a new output directory; existing packet files are refused. Tests compare
rebuilt bytes, refuse overwrites, validate scopes/report contracts, bind hashes,
verify exact source reports and delivered evidence, and reproduce local rejection
of the fabricated citation. Passing tests establish packet integrity, not label
correctness, semantic verification or readiness for deployment.

No production code, provider calls or paid authorization are part of this work.
Before execution, approve the model and explicit request, token, time and spending
bounds, and implement a host adapter that fails closed on invalid or incomplete
coverage. Preserve first-pass judgments before revealing these labels to a reviewer.
